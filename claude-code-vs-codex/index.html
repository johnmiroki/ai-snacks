Claude Code vs Codex CLI

Two terminal coding agents, command for command. Where both do the same job, this page puts them side by side and quotes each tool's own description of itself rather than paraphrasing either. What is left over on each side is the part that has no counterpart at all. Built from the same inventories as the Claude Code and Codex index pages, so every name here links back to its entry.

/ /

The shape of each surface

Same job, two very different places to type it

Before any single command: the two tools disagree about where a coding agent's controls belong. Claude Code puts them at the prompt, behind a /. Codex puts them in your shell, as subcommands. That one choice explains most of the differences further down — including why Codex needs 68 subcommands and Claude Code needs 14.

Claude Code 2.1.220

143 commands

  • 96 native slash
  • 23 bundled skills
  • 14 shell subcommands
  • 10 hidden

Almost everything is a slash command, and the shell side is a short list of things you do to Claude Code rather than with it — install it, log in, manage plugins.

Codex CLI 0.146.0

122 commands

  • 46 slash commands
  • 68 shell subcommands
  • 8 hidden

The shell side is the bigger half, and it goes deep: codex app-server daemon enable-remote-control is a real command. Codex expects to be scripted and embedded, not only typed at.

The opinion section, marked as such

Everything above this line is measured. This part is not — it is a reading of those measurements, and someone who weighs sandboxing against session ergonomics differently would write it differently. Both tools are good. The question worth asking is not which is better but which set of assumptions matches how you work.

Reach for Claude Code when

  • You want the session itself to be the workspace. Claude Code puts almost everything behind a /, including things Codex settles at launch — move to another directory, change effort, swap the model, background the whole session and get the terminal back.
  • You want to undo. /rewind has no counterpart on the Codex side of this page.
  • You lean on skills and subagents. 35 prompts ship in the binary, agents are files you write, and /subtask, /fork and /workflows exist to fan work out and collect it.
  • You want the model choice to include Bedrock or Vertex.

Reach for Codex when

  • You want the agent under a sandbox you can reason about — and reuse. Approval policy and sandbox policy are separate flags with named values, and codex sandbox will wrap any command, not just the agent's.
  • You are building on top of it. codex mcp-server makes Codex a tool other agents call; codex app-server hands you a protocol daemon with generated schema and TypeScript bindings.
  • You want the tool configured as data. One TOML file, layered profiles, and -c any.key=value for a single run.
  • You want to run against a local model — --oss with LM Studio or Ollama.
  • You want to see the feature flags rather than discover them.

And mostly

  • Neither list is a ranking, and the overlap is the real story: 43 jobs on this page have a command on both sides, several with the same name. Both ship hooks, MCP, plugins, skills, plan mode, a review command, a memory system and a desktop hand-off. Both also ship a command that imports the other one's setup, which tells you what the vendors expect you to be doing.

Where the two halves came from. The command comparison is built from the same two inventories as the index pages on this site, and adds nothing to them: Claude Code's names and descriptions were parsed out of the installed binary, Codex's were read off the running / picker and a recursive walk of codex --help. Descriptions are reproduced as the builds carry them. Every name links back to its full entry.

The pairing is editorial; the complement is not. Which two commands count as “the same job” is a judgement made by hand, and the reason both descriptions are printed is so that judgement can be checked rather than trusted. The two only in lists are then computed as whatever no pair claimed — so a bad pairing shows up as a missing entry, and every command in both inventories appears exactly once on this page.

The capability table was measured on one machine. Sandbox modes, approval policies, config paths and provider options come from claude --help and codex --help on the builds named above, plus the shape of the files in ~/.claude and ~/.codex. Where a claim could not be established that way it is marked rather than rounded off — see the note under the table.

Two builds, one moment. Both tools ship fast, and both resolve part of their surface at run time: Codex against 100 feature flags and your account, Claude Code against its own gating. A count here is the count on these two builds, not a permanent fact about either tool.
